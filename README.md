# oj_of_honhax

一个记录**原创算法题**的个人题库：从本地项目里提炼一个具体算法点，把它改写成可评测的算法题；题目与答案分离，答案必须经过可复现的验证。

难度基准是 `example.md` 的 8 星；本项目的目标通常是**再难两个梯队（9~10 星）**，强调“能写出来、但不容易写对”的题，而不是模板题。

## 难度与分层

星级描述题目本身的难度，分层是星级对应的训练档位：

| 星级 | 分层 |
| --- | --- |
| 1~3 星 | 入门 |
| 4~5 星 | 基础 |
| 6~7 星 | 熟练 |
| 8 星 | 提升 |
| 9 星 | 困难 |
| 10 星 | 专家 |

边界星级（3 星）按更高分层归档为「基础」。每道题的题面头部同时标注星级与分层。

## 目录结构

```
oj_of_honhax/
├── README.md                 # 本文件：项目说明与目录约定
├── example.md                # 格式参考（外部样例，不占用正式编号）
│
├── problems/                 # 题面：<四位编号>.md（0001.md、0002.md、……）
├── solutions/                # 题解：与题面同编号（0001.md、0002.md、……）
└── verify/                   # 验证代码：<编号>/solution.cpp + brute.cpp
```

## 各目录与文件说明

### `problems/` — 题面

存放正式题面，一题一个文件，文件名为四位编号：`0001.md`、`0002.md`……

题面只包含“做题需要知道的信息”：

- 题目描述、输入/输出格式、样例、数据范围；
- 必要的定义与约定（例如记号顺序、合法状态判定）；
- 少量不剧透解法的提示。

**不**在题面里写解法、复杂度、实现细节。

### `solutions/` — 题解

与 `problems/` **一一对应、同编号**：`0001.md` 对应 `0001` 题。

每题题解固定包含：

1. **出题来源**：来自哪个本地项目、哪个算法点；若该项目有远端仓库则附链接（仅本人推送的仓库才作为“项目链接”，第三方项目会注明“上游参考”）；
2. **关键性质/建模**：把项目里的机制抽象成可证明的模型；
3. **算法**：核心步骤与易错点；
4. **正确性证明**：引理式说明，至少覆盖“为什么是最优/为什么计数不重不漏”；
5. **复杂度**：时间、内存；
6. **验证记录**：实际跑过的自检、对拍、重放结果；
7. **参考代码**：完整可编译代码（与 `verify/` 中的标程一致）。

### `verify/<编号>/` — 验证代码

每题的验证材料，目录名与题号一致：

- `solution.cpp`：参考实现/标程。应能直接编译，并通过题面样例；通常带 `--selftest` 之类的自检入口。
- `brute.cpp`：独立暴力/对拍器。要求尽量**换一种实现路径**（例如用几何模拟而不是状态编码），用来给标程制造独立证据；小深度随机对拍是每题的必做项。

验证的原则：

- 能用**已知理论结果**校验的，优先校验（如全状态距离分布、已知最优值）；
- 能用**独立实现**对拍的，必须对拍（距离/计数/构造方案逐项比较）；
- 构造类题目要能**独立重放**，证明输出确实合法；
- 验证结论写进 `solutions/<编号>.md` 的“验证记录”，而不是只留在终端里。

### `example.md`

格式参考文件，保留原始样例（题目 + 思路 + 代码），**不占用正式编号**，也不作为项目内的正式题目。

## 编号与命名约定

- 四位十进制编号，从 `0001` 开始顺序分配；
- 同一道题的三处编号必须一致：

```
problems/0001.md  ↔  solutions/0001.md  ↔  verify/0001/
```

- 题解里的交叉链接使用相对路径，例如 `../problems/0001.md`；
- 代码文件统一用 `.cpp`，按 C++17 编写；
- 题面中的时空限制写在文件头部引用块里，例如：

```
> 内存限制：256MB｜时间限制：3000ms｜难度：10 星｜分层：专家
> 解决次数：0｜提交次数：0
```

## 新增一题的流程

1. 在本地项目里选一个**边界清晰**的算法点（最好能说清“输入是什么、要输出什么、为什么难”）；
2. 把它改写成自包含的题面，确定数据范围、时空限制、样例，并标注**星级与分层**；
3. 先写标程 `verify/<编号>/solution.cpp`，再写独立暴力 `brute.cpp`；
4. 用小数据对拍、用已知结论校验，记录结果；
5. 写 `solutions/<编号>.md`，附上来源、证明、复杂度、验证记录和完整代码；
6. 在 `problems/<编号>.md` 中只保留题面信息；
7. 更新本 README 的“已收录题目”表。

## 复跑验证

以 0001 为例（Windows PowerShell / 任意带 g++ 的环境）：

```powershell
g++ -O2 -std=c++17 -o solution verify/0001/solution.cpp
g++ -O2 -std=c++17 -o brute    verify/0001/brute.cpp

# 全状态自检（应输出 distribution check: PASS）
.\solution.exe --selftest

# 对拍：把生成的询问同时喂给两个程序，比较输出
Get-Content cases.txt | .\solution.exe > sol.txt
Get-Content cases.txt | .\brute.exe    > brute.txt
Compare-Object (Get-Content sol.txt) (Get-Content brute.txt)
```

`brute.cpp` 只适合浅层数据；深层数据的正确性依赖标程的全状态预计算，并用独立模拟重放输出方案。

## 约定

- 题目与答案严格分离，题面不剧透；
- 每道题都能追溯到一个具体的项目算法点，而不是凭空造题；
- “尽量还原”指保留算法核心与约束结构，允许为可评测性缩小规模（例如把 3×3 最优解降为 2×2）；
- 答案必须验证，验证必须可复现；
- 第三方项目只附上游参考链接，本人远端仓库才标注为项目链接。
